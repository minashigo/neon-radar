# Синхронне виконання спільного портфеля Neon Radar

Дата: 28.10.2026. База: 656d1d0. Змінено обробку спільного портфеля; індикатори, пороги, торгові витрати та ліміти ризику не оптимізувалися.

## Результат

Усунуто залежність OHLC-виконання в ForwardPaperTradingEngine від черги символів. Відтворений раніше збиток BTC на закритті свічки більше не може скасувати вхід ETH на відкритті тієї ж свічки. Внутрішньосвічковий прибуток також не фінансує раніший вхід іншої монети.

Верифікація:

- 26 нових тестових випадків у test_synchronized_paper.py; перші 18 до реалізації давали 15 failures і 3 passes.
- Один із тестів перебрав усі 720 перестановок шести монет: повні об'єкти стану, закритих угод, входів, резервів та проміжних спостережень equity збігаються.
- Повторний прогін 4H за 01.01–31.03.2025 виконаний двічі, із прямим і зворотним списком монет. Усі поля угод, кривої капіталу, витрат та метрик збігаються точно. Відрізняється лише записаний вхідний порядок символів.
- Повний набір: 639 passed, 1 skipped. Ruff для змінених файлів — без зауважень. Пропущений тест існував раніше.

## Фази однієї свічки

| Фаза | Дія | Що доступне наступним входам |
|---|---|---|
| Підготовка | Отримати закриті свічки для всіх налаштованих символів, потім HTF/funding | До завершення мережевих запитів нові заявки цього циклу не реєструються |
| Спільне відкриття | Одночасно оцінити відкриті позиції всіх символів за O; оновити drawdown | Єдиний snapshot цін початку інтервалу |
| Gap-виходи | Закрити раніше відкриті позиції, які вже перетнули SL/TP на O | Реалізований результат, відомий на початку свічки |
| Входи | Спочатку заявки, доступні на O, потім можливі дотики всередині свічки; повторно перевірити ризик | Резерви інших заявок враховуються; внутрішньосвічкові виходи ще не звільняють гроші |
| Внутрішньосвічкові виходи | Обробити SL/TP за наявними консервативними правилами OHLC | Нових входів після цих виходів у цій свічці вже немає |
| Спільне закриття | Одночасно оцінити всі залишені позиції за C; оновити drawdown | Повний snapshot кінця інтервалу |
| Сигнали | Розрахувати сигнали й зарезервувати нові заявки для наступного виконання | Однаковий рахунок на закритті; резерви збільшуються послідовно |

Під час фаз виконання та реєстрації сигналів немає await на біржові запити. Це прибирає можливість заповнити нову заявку раннього символу під час очікування HTF/funding для пізнішого символу в тому ж poll_cycle.

Фіксований пріоритет розподілу бюджету збережений як у канонічному списку: BTC, ETH, SOL, BNB, XRP, ADA. Інші символи йдуть після них у лексикографічному порядку. Це правило розв'язання одночасних заявок, а не рейтинг сигналів або відновлення послідовності біржових тиків. Уже наявні резерви не скасовуються заради нових заявок більш пріоритетної монети.

## Неузгоджені дані та відновлення

- Якщо немає придатної базової свічки хоча б для одного символу або останні закриті свічки мають різні open_time, весь портфельний цикл відкладається з warning. Позиції, заявки й last_processed_candles цього циклу не змінюються.
- Це свідомий компроміс доступності: тимчасова проблема одного символу затримує OHLC-обробку всього спільного портфеля. Жодні реальні ордери не розміщуються.
- Однакова свічка після повторного опитування/перезапуску не виконується вдруге. При відновленні старого несинхронного стану не відтворюються окремі запізнілі символи поверх уже обробленого інтервалу: потрібна новіша спільна свічка.
- Після виконання групи маркери всіх символів оновлюються до початку аналізу. Помилка окремого розрахунку сигналу не змушує повторювати виконані входи/виходи наступного разу.
- Збережено попередню модель latest-closed polling: це не новий механізм відновлення кожної пропущеної свічки після довгого відключення.
- new_fills тепер повертається з фактичних подій виконання, а не зі зрізу поточного списку позицій. Тому вхід не губиться, якщо стара позиція одночасно закрилась або нова позиція вже встигла закритися в цій же групі.

Це не абляція кожної окремої фази і не доказ статистично стійкої переваги стратегії.

## API та обмеження

- Новий process_market_batch приймає весь одночасний набір символів. Різні часові межі відхиляються до зміни стану. Всі None close_time допустимі для групи point ticks; поєднання різних/невідомих меж в одному наборі відхиляється. ForwardPaperTradingEngine нормалізує відсутній close_time за своєю тривалістю свічки.
- process_market_tick збережено як односимвольний адаптер для сумісності з бектестером і point ticks. Цикл одиничних викликів для різних повних OHLC-свічок не є синхронним batch. Старий demonstrate_order_bias.py навмисно демонструє саме неправильний спосіб; для нового шляху є тести batch і два повні історичні прогони.
- Це спільні фази моделі OHLC, а не точний календар біржових мікроподій. Рух усередині свічки, ліквідність, черга й часткові виконання невідомі. Консервативно не використовується внутрішньосвічкове звільнення капіталу для інших входів тієї ж свічки.
- Перевірений режим — синхронні закриті OHLC-бари. Змішування повного replay вже обробленого інтервалу та паралельного потоку live ticks потребує окремої політики дедуплікації подій; ця робота не доводить таку сумісність.
- Funding і далі використовує умовність (entry,exit], 8-годинну сітку та наближення через номінал виходу. Replay відхиляє невідповідний календар замість мовчазного припущення. Перед II–IV кварталами потрібні перевірка реальних інтервалів і точніший облік mark price на settlement.
- MDD у дослідницькому replay — оцінка за його наявними snapshot/event-спостереженнями; без тиків це не точна внутрішньосвічкова біржова просадка.
- Нова історична перевірка виконана для 4H, а не для 1H; попередні висновки про 1H цією роботою не перевірялись повторно.
